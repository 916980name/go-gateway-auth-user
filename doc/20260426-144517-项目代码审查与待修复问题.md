## 一、项目优点

1. **中间件链架构** -- `Proxy`/`Middleware` 类型定义(`func(ctx, *http.Request) (ctx, *http.Response, error)`)组合性好、可测试、排序显式
2. **Build tag 分离 debug/release** -- `//go:build debug` 条件编译避免生产环境运行时条件判断开销
3. **Redis Lua 令牌桶限流** -- 原子性操作避免 GET/SET 竞态；双后端(内存+Redis)设计实用
4. **优雅关闭** -- 缓冲信号通道 + context 超时 + `http.Server.Shutdown` 正确实现
5. **JWT 算法固定** -- `VerifyJWTRSA` 正确验证 `SigningMethodRSA`，防止算法混淆攻击
6. **Context 请求追踪** -- 使用未导出 struct key 传递 request ID/IP/user 是地道的 Go 做法

## 二、严重问题 (CRITICAL - 必须修复)

### C1. IP 伪造绕过限流和黑名单

- **文件**: `pkg/middleware/requestFilter.go:66-90`
- **问题**: `getClientIP` 无条件信任 `X-Forwarded-For` 和 `X-Real-IP` header，攻击者可轮换 header 值绕过所有 IP 限制，也可伪造他人 IP 使其被限流
- **修复方案**: 增加可配置的受信代理 CIDR 列表，仅在请求来自受信代理时信任这些 header，否则使用 `RemoteAddr`

### C2. LogoutFilter 未检查类型断言导致 panic

- **文件**: `pkg/middleware/loginLogoutFilter.go:175`
- **代码**: `ctx.Value(common.Trace_request_user{}).(string)`
- **问题**: 用户未认证时 context value 为 nil，直接类型断言会 panic
- **修复方案**: 使用 comma-ok 模式 `user, ok := ctx.Value(...).(string)`，`ok` 为 false 时返回 401

### C3. generateAccessToken 未检查 username 断言导致 panic

- **文件**: `pkg/middleware/common.go:48`
- **代码**: `(*onlineCache).Set(ctx, getOnlineCacheKey(m["username"].(string)), md5Str)`
- **问题**: 后端响应无 `username` 字段时 panic
- **修复方案**: 断言前检查 nil 和类型

### C4. 代理响应 Body 未关闭 -- 资源泄漏

- **文件**: `pkg/proxy/proxy.go:97-125`
- **问题**: `HandleProxyResponse` 中 `resp.Body` 从未 close，每个请求泄漏 TCP 连接，最终耗尽文件描述符
- **修复方案**: 在 `resp` 非 nil 检查后添加 `defer resp.Body.Close()`

### C5. 无连接池且禁用连接复用 -- 端口耗尽

- **文件**: `pkg/proxy/proxy.go:11,41`
- **问题**: 默认 `http.Client` 的 `MaxIdleConnsPerHost` 仅为 2，加上 `r.Close = true` 禁用复用，每个请求新建 TCP 连接
- **修复方案**: 移除 `r.Close = true`，配置自定义 `http.Transport`（设置 `MaxIdleConns`、`MaxIdleConnsPerHost`、`IdleConnTimeout`）

### C6. RSA 私钥在配置模板中提交到仓库

- **文件**: `configs/api-gateway.yaml.template`
- **问题**: 配置模板包含完整 RSA 私钥并已提交仓库
- **修复方案**: 替换为占位符文本，密钥加载改用环境变量或密钥管理服务

### C7. 全局 RSA 密钥变量多站点互相覆盖

- **文件**: `internal/api-gateway/config.go:10-23`
- **问题**: 多个 site 循环调用 `initRSA` 时后者覆盖前者，所有站点共用最后一个的密钥，多站点 JWT 隔离失效
- **修复方案**: 将 RSA 密钥对存储在 per-site 的 config/middleware requirements 结构体中，而非包级全局变量

## 三、重要问题 (IMPORTANT - 应该修复)

### I1. 启动日志泄露完整配置含密钥

- **文件**: `internal/api-gateway/gateway.go:94-95`
- **代码**: `settings, _ := json.Marshal(viper.AllSettings()); log.Infow(string(settings))`
- **问题**: INFO 级别输出完整配置，包含 RSA 私钥、Redis 连接字符串等敏感信息
- **修复方案**: 脱敏后再输出，或仅输出非敏感配置项

### I2. TLS 模式优雅关闭失效

- **文件**: `internal/api-gateway/gateway.go:127-129`
- **问题**: `ListenAndServeTLS` 错误处理缺少 `!errors.Is(err, http.ErrServerClosed)` 判断，优雅关闭时会调用 `log.Fatalw` 导致 `os.Exit(1)`
- **修复方案**: 与非 TLS 路径保持一致，添加 `ErrServerClosed` 判断

### I3. Recovery 中间件不返回 HTTP 响应

- **文件**: `pkg/middleware/recovery/recovery.go:37-45`
- **问题**: 捕获 panic 后仅记录日志，不向客户端写入任何响应，客户端收到空响应或连接重置
- **修复方案**: recover 后返回 500 Internal Server Error

### I4. Cookie 缺少安全标志

- **文件**: `pkg/util/httpResponseUtil.go`
- **问题**: JWT token cookie 未设置 `Secure`(MITM)、`HttpOnly`(XSS)、`SameSite`(CSRF) 属性
- **修复方案**: 设置 `HttpOnly=true`、`Secure=true`(TLS 时)、`SameSite=Lax/Strict`

### I5. MD5 做 token 指纹

- **文件**: `pkg/common/stringsutils.go:16`, `pkg/middleware/authFilter.go:69`
- **问题**: MD5 已被密码学证明不安全，碰撞攻击可行
- **修复方案**: 替换为 `crypto/sha256`

### I6. Redis 缓存 Duration 计算整数溢出

- **文件**: `internal/api-gateway/cache.go:54`
- **代码**: `time.Duration(cconf.DefaulExpireMinute*int(time.Minute))`
- **问题**: `int(time.Minute)` = 60000000000，与分钟数相乘后 int 溢出；对比第 49 行内存缓存写法是正确的
- **修复方案**: 改为 `time.Duration(cconf.DefaulExpireMinute) * time.Minute`

### I7. InitRedis 无 nil 检查导致 panic

- **文件**: `internal/api-gateway/cache.go:73-79`
- **问题**: `config.Global().Db` 或 `.Redis` 为 nil 时(如未配置 Redis)直接 panic
- **修复方案**: 调用前添加 nil 检查

### I8. Login filter 读取响应体后未重置 Body

- **文件**: `pkg/middleware/loginLogoutFilter.go:87-106`
- **问题**: `httputil.DumpResponse` 消耗了 `resp.Body`，返回给客户端的 Body 为空
- **修复方案**: 读取后用 `io.NopCloser(bytes.NewReader(bodyBytes))` 重置 `resp.Body`

### I9. RefreshToken 不验证 access token 是否过期

- **文件**: `pkg/middleware/refreshTokenHandler.go:38-43`
- **问题**: 接受任何 access token（包括未过期的），客户端可无限刷新不重新认证
- **修复方案**: 仅在 access token 已过期（或接近过期）时允许刷新
